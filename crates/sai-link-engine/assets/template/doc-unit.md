# 実装計画書の書式（doc-unit）

**1 つの実装計画書 = 1 人の worker が 1 回で終えられる作業。** worker はこの文書と追加指示だけで作業する。他の計画書やガイドは読まない前提で書く。

- ファイル名: `unit-<ID>-<短い英語名>.md`（改訂は末尾に `-r2`）
- description: `実装計画書 <ID>: <件名>`
- 別のモデルが文脈なしで読んで実装できる細かさで書く。変更する場所は `path:line` と既存の関数名・型名で示す。変更後の動きは、入出力の例・コード片・図で示す。「適切に」「必要に応じて」で終わらせない。

```markdown
# 実装計画書 <ID>: <件名>

## 目的
<この作業で何ができるようになるか。1〜3 文>

## 背景
<なぜ必要か。worker が判断に迷ったときの拠り所になる事実>

## 前提（着手時点のコードの状態）
- <事実> — `path/file.rs:120`
- <先に終わっているべき作業の ID と、それで何が変わっているか>

## 変更内容
### 1. <変更の単位>
- 対象: `path/file.rs:120-180` の `fn_name`
- 現状: <今どう動いているか>
- 変更後: <どう動くべきか。入出力の例、コード片、図>

## 共有契約（他の作業と共有する取り決め。worker は変えない）
- <型・関数の形・ファイル形式・CLI などの外部仕様。全文を写す>

## ファイルの所有権
- 書いてよい: `a.rs`, `b.rs`
- 読むだけ: `c.rs`
- 触らない: <他の作業が書く範囲>

## 完了条件
- [ ] AC1: <確かめられる条件。テスト名・コマンド・目で見て分かる結果>

## 検証
<実行するコマンドと、期待する結果>

## 決定事項と理由
- <決定> — 理由: <…> / 採用しなかった案: <…>

## 要確認
- <未確定の点と、決まるまでの扱い。無ければ「なし」>
```
